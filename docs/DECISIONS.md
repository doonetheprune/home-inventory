# Decisions

Choices made with the user that aren't in the original brief. Newest last within each phase.

## Phase 0: interface design

- **Name:** the project and add-on are called **Larder**.
- **Look:** its own modern style, not Home Assistant's. Deep cobalt blue accent, cool neutral greys, light and dark themes.
- **Home screen:** a dashboard with a large Scan button, Add by name and Put away (on a phone; on a big screen they're in the sidebar, see "After the owner tried it"); a "Going shopping?" card with every shop and how much to buy there (it first suggested one shop; see "After the owner tried it"); then use soon, running low, away from home and deliveries on the way.
- **"Any shop" items:** each shop has a list of categories it sells (e.g. Tesco: groceries and household; Toolstation: hardware and tools). An item with no preferred shop only appears on the lists of shops that sell its category.
- **Scanning:** always starts in Add mode. Use, move, put away and look up are picked before scanning.
- **Wording:** the app says **Places**, not Locations.
- **Desktop:** the same app adapts to wide screens with a sidebar and multi-column layouts, rather than being a separate design.
- **Search first:** search is the main way in. It runs across the top of every screen on desktop and is the first thing on Home on a phone. Results carry + and − buttons to add or use stock directly; if nothing matches, the first option is to add it as a new item.
- **Search keys:** Enter opens the highlighted result. ↑ and ↓ count up or down on a stock result, then Enter adds or uses that many. Tab moves between results. Esc cancels a count, then closes.
- **Search scope:** search covers everything, with results in sections: stock, shopping lists, places, scenarios, wish list, shops and saved recipes.
- **Out of place:** an item has a usual place and, optionally, a place it is in right now (usually in the Garage, now in the Shed). The app calls these items **Out of place**, not "away from home".

## After the owner tried it

Changes the owner asked for after trying the example household.

- **Going shopping:** every shop gets the same tile, with how many to buy there and its name, in the order set under Shops. No shop is singled out (the headline no longer names one either).
- **Stock by type:** Stock opens on a card per type of thing (Food, Household, Tools & DIY…, from the categories) with how many items and what needs attention; "Everything" is still a card. A type's list is grouped by place, with tabs to switch type and the status filters (low, use soon…) as their own row.
- **Adding at another place:** "Add somewhere else" on an item's "Where it is", and from the stock pane on desktop. It asks for the place rather than assuming the usual one.
- **Something's moved, from Home:** pick the item and where it is now; it shows as out of place until it's put back (the same as the `move_item` tool with `permanent: false`).
- **Prices by weight:** the usual price can be shown per item, per 100 g or per kg (per 100 ml or per litre for liquids), chosen on the price card. Things counted in bags or tins need their size once ("1 bag = 200 g") to be priced by weight; since 0.10.0 that's the item's **Weight**, which the price card shows and changes. Pack checks take a size and unit, so a shelf label like "£3.50/kg" can be compared. Assistants get `convert_price`, and `check_price` and `set_usual_price` take a unit (`set_item_size` went in 0.10.0: the Weight is set with `change_item`).
- **Shop locations** (a module): **Find nearby** on each shop searches OpenStreetMap for its branches around home; **Add to Home Assistant as zones** makes them zones; **Create the automation** saves one automation that sends that shop's list to a person's phone when they arrive. Larder makes these through Home Assistant's own API (as the Supervisor for the add-on, or with an admin's token), and always offers the same as YAML to paste in. Tried against a real Home Assistant 2026.2: zones made and updated, the automation loaded, and a phone arriving in a zone got "7 things to get at Aldi: …".
- **Recipe ratios and presets:** an ingredient can have a ratio, how much goes in for the recipe as saved in its own measure (2 eggs, 100 g flour, 300 ml milk). Larder does the maths, not the assistant: "I've only got 2 eggs" goes to `get_recipe` as `have`, and with several amounts the one that runs out first wins. Amounts made often are kept as named presets, each so many times the recipe as saved; one can be the default, used without asking unless another is named. With presets but no default, the assistant is told to ask which. After working amounts out, the assistant is prompted to offer saving them as a preset (`save_recipe_preset`). The app has the same: preset chips, **I've got…** and **Save as preset**, and cooking takes the amounts shown. `save_recipe` can now change a saved recipe, so ratios can be added to older ones.
- **Places an item is kept in** (0.7.4): an item can live in several places, and running out in one doesn't forget it. A place joins when stock is added there (not when it's only out of place there for now) and stays at 0, ready for more, until the owner takes it off (the ✕ beside it at 0) or moves its stock somewhere else for good. Removing a place takes it off every item. Assistants and Home Assistant say how many are in each place ("1 jar in Kitchen and 1 jar in Larder", "none in Garage"), not just the places.
- **Adding stock to a place is a quick add:** the search comes first; each match shows how many are here and in total, with − and + for how many should be here and a tick to save. No second step, and several items can be done without leaving. To sort shows under the search while nothing's typed.
- **Add by photo names the product, not just the kind** (0.7.5, the owner's ask after Twinings Sleep came out as "Herbal tea": "that's a bit too vague"). The name always has the variety, flavour or type ("Peppermint tea bags", "Semi-skimmed milk"), and the brand when the product is that brand's own blend or range ("Twinings Sleep tea bags", "Marmite"); everyday things where any brand will do keep a plain name ("Baked beans"), so "milk is milk" from the brief still holds. The plain kind ("Herbal tea") becomes the item's first other name, and the scanner's card also offers an item the household keeps for that kind.
- **Add by photo can look things up online** (0.7.5, the owner hoped "the AI model would be able to search online"): when the photo doesn't show which product it is or its size, Claude (web search) or Gemini (Google Search) searches, at most twice a photo, and the card names the sites it used. **Look things up online** in Settings → AI switches it off.
- **How fast it's used, and what it comes in** (*Counted in, Comes in and counting again were replaced in 0.10.0: see "Bought in, Contains, Weight". We use and Take them out of stock for me stay.* 0.9.0, the owner's ask: "tea bags I have every single day: if I bought a box of 20, we know how long it's going to last", without the app getting more confusing, and happy to lose features or re-enter data for the right design; it replaces 0.8.2's **Each one lasts** and **Use the next one automatically**, and pricing's measures). Designed twice independently, then reviewed independently before it was built. An item is **Counted in** the single thing that's used (a tea bag, a roll, a sensor). It can **Come in** one pack ("a box of 20"): adding 1 box adds 20 tea bags, the item says "37 tea bags · about 2 boxes", the shopping list buys whole boxes, and assistants and Home Assistant can give amounts in boxes. **We use** says how fast, always in what it's counted in ("1 tea bag a day", "1 sensor every 2 weeks"), so "1 box a day" can't be said by mistake; it gives "Enough until 14 Dec". **Take them out of stock for me** has Larder take that many out each day or period by itself (the hourly check, catching up if Larder was off, stopping at none, starting again the day more is added), so Use is only for an extra one; **Came off early: start the next one now** starts a new one today. Without it, each Use starts one (the sensor case, as 0.8.2 did). Low is only **Running low below** (shown as "a week's worth"), not "runs out within the warning days". Something counted in boxes so far can be **counted again** in what's inside: changing Counted in to tea bags, with Comes in a box of 20, offers "Count them as 40 tea bags", which multiplies the stock, orders, minimum, stock-up amount and usage, and the modules rescale their own numbers (prices, online shop packs, recipe amounts). It's in the core, not a module, because it changes stock and what counts as low, which only the core does.
- **Opened, not finished** (0.8.2, the owner's ask: "last one open only if marked as open, not if quantity is 1"). Anything can have one open: **Use** has **Opened, still using it**, which takes it out of the count and shows "One open since 3 Nov" until **Finished the open one**. With none left and one open, it's **Last one open** (low, on the list); with none open, it's **Out**. A quantity of 1 is never taken to mean open. Things with a usage use the same marker for the one in use: **Finished early** stops it (and stops Larder taking them out until one is started again).
- **Several measures of an item** (0.8.2; replaced in 0.9.0, and again in 0.10.0: see "Bought in, Contains, Weight"). "1 pack = 5 items" became the item's pack, in the core (counted in items, comes in packs of 5), so stock, the shopping list and assistants use it too, not just prices; since 0.10.0 it's bought in packs, containing 5 pieces. The weight or volume of one ("1 bag = 200 g") stayed on the price card, and moved to the item's **Weight** in 0.10.0. A separate usual price per measure (loose by the kg) went: the usual price is per what it's bought in, and can be shown per what it contains or by weight.
- **Purchase history** (0.8.2, the owner's ask: "a history of purchases for every item with price and evidence, a picture of the receipt or 'online order on x date', to report on later"). The `purchases` module keeps every purchase from the core's events, however it came in: ticked off a shopping list, a receipt (its photo and date are kept), an item's Add with a price, shop or receipt photo, an assistant's `add_stock` or `bought`, and orders when they arrive (the order number, the day it was ordered, and its price when the order email or the online basket gave one). Each item's page lists what it was bought for; the **Purchases** page has what was spent this month, last month, this year or ever, by shop, item and month. A purchase can be corrected or have its receipt's photo added later; that never changes stock.
- **Assistants can do what the app does** (0.8.2, the owner's ask: "MCP should support all of these features plus ones added"). New tools for opening and finishing, prices, purchase history and spending, lists of items by status, category or place, what's in a place, what a code is, several things bought at once, batteries and devices, order email lines, and online shopping packs; and the missing options on the others (brands, prices, notes, links, places an item's no longer kept in, moving from To sort, putting back from one place, a recipe's shopping at any amount).
- **Assistants ask less** (0.9.1, the owner's ask: the Claude app "often asks for permissions when using the voice chat", even after pressing Allow). The Claude app asks before every call to a tool marked destructive, and pressing Allow in a chat doesn't remember it. Everyday changes that doing the opposite undoes, and that stock history records, are no longer marked destructive: `use_stock`, `finish_item`, `move_item`, `mark_arrived`, `remove_from_shopping_list`, `batteries_replaced` and `confirm_cooking` (which only runs after the person agreed to `propose_cooking`'s list). Removing something or overwriting what was set still is: `remove_*`, `forget_*`, `change_*`, `correct_stock`, `cancel_order`, prices, buying rules, links and order lines. `propose_cooking` is marked read-only (it keeps its list for a few hours for `confirm_cooking`, but changes nothing in the house). To stop the asking altogether, set Larder's tools to Always allow in the Claude app (docs/mcp.md). *Alternative:* keep every stock change marked destructive and rely on that setting alone.
- **Assistants keep the boxes** (*replaced in 0.10.0: the item is bought in boxes, containing 20 tea bags; see "Bought in, Contains, Weight".* 0.9.2, after the owner asked the Claude app to say how many tea bags are in a box: it counted them as 80 tea bags, said only that, was asked "there's four boxes, but there should be a way to say there's 20", undid it and wrote "20 tea bags per box" in the notes, and never got as far as how many are used a day). Nothing in the tools was missing; the assistant didn't know the boxes are kept. Now the instructions an assistant gets on connecting say how packs work, `change_item` says the boxes are still shown and asks for a usage when there's none, "counted in boxes, comes in boxes" is answered with how to do it, a rename says what the numbers now read as, and lists show packs ("80 tea bags (4 boxes)"). Going back from tea bags to boxes (dividing) is still not offered: a pack already shows the boxes. *Alternative:* let an item be counted in its pack and know what's inside, which brings back "which one does 1 mean" (decision 44).
- **Bought in, Contains, Weight** (0.10.0, agreed with the owner on 8 November 2026 in `docs/plans/units.md`, after two chats in the Claude app: asked to record that a box of Twinings Sleep holds 20 tea bags, the assistant followed 0.9.0's "count the single thing that's used" and counted 80 tea bags, then undid it when the owner wanted to keep counting boxes and wrote "20 tea bags per box" in the notes; asked to set a 400 g jar of decaf to "four grams a day", it could only set "1 jar every 100 days"). It replaces 0.9.0's Counted in, Comes in and counting again, and 0.10.0 as first built ("Used by weight", PR #36, held and never released), which between them gave an item four overlapping ideas (Counted in, Comes in, Weighs, a usage unit) and kept unit words in six places. Now an item has three:
  - **Bought in**: what you buy and count it in, from the unit list: bag, box, jar, roll, each… or, for things bought loose, g or ml. Stock, minimums, stock-up amounts, orders and history are always in this.
  - **Contains**: what one holds, as printed on the pack, if given. Either a number of something on the list (a box contains 20 tea bags, a roll contains 200 sheets) or an amount by weight or volume (a bag contains 1 kg, a bottle contains 4 pints).
  - **Weight**: what one weighs in g, or holds in ml for liquids, if given, and it can be given for anything (a box of Sleep weighs 30 g). Filled in from Contains when Contains is an amount. It's the only thing any sum in g or ml uses.
  - **We use** says how fast it goes, in what it's bought in, in what it contains when that's a count, or in any weight or volume once there's a Weight, kept as said ("1 tea bag a day", "4 g a day"). The **unit list** is long and fixed, each word a count, a weight or a volume with its singular and plural; the household adds its own count words in Settings → **Units** (assistants: `list_units`, `add_unit`). There's never a free-text "other".
  - In the code, only `src/core/services/units.ts` knows about units, and only its converter turns an amount into what an item is bought in (`AGENTS.md`).

  Decided by the owner:
  1. **Stock is counted in what you buy.** Using one at a time out of a pack isn't a feature: "it would be up to the user and how they create them". Toilet rolls are bought in rolls, containing 200 sheets. The daily counter can take out part of a box, and a count can be corrected in what it contains ("I've got 3 boxes left and I've used 5 from the box"), "only to readjust the daily counter".
  2. **One size per item:** "you tend to just buy one size of something". There are no sizes per brand or barcode. A different size is adjusted by hand, or kept as its own item.
  3. **No multipacks:** a 6-pack of beans is 6 tins added.
  4. **Weight** "should always be the size in grams. So even if I say it's a kilogram, it always goes back down to grams" (millilitres for liquids). It's "never mandatory, but could always be filled in, even for sleep tea bags", and it's "the only column used for calculations": recipes, prices per 100 g or per kg, usage by weight. "If we get the code to look at all three columns in those scenarios, we'll have major tech debt."
  5. **Units** come from "a fixed list, but it needs to be an extensive list and we should never have other, but we should have the ability to add a new [unit]. That also needs to be on the MCP."
  6. **Moving old data over** doesn't have to be perfect, "as long as they're cleanly flagged in the interface" so the owner can fix them. When 0.10.0 first starts, kg becomes g and L becomes ml (the numbers × 1000); a pack is turned round (counted in tea bags, comes in a box of 20 becomes bought in boxes, containing 20 tea bags, with the numbers ÷ 20); and pricing's weight of one moves onto the item's Weight. Turned-round packs and unit words not on the list ("4 pint bottle") are flagged **To tidy** with the reason: in Stock, as a banner on the item's page (**Looks right** clears it, and so does saving from Edit), and for assistants (`get_item`, `list_items` with `to_tidy`).
  7. **The word is "Bought in".** "Bought from" would mean the shop.

  Asked while it was built (9 November 2026), the owner chose:
  - **A pack of things counted "each"** (each, comes in packs of 5) becomes bought in packs, containing 5 pieces, flagged To tidy like any other pack. *Alternative:* keep it in each and drop the pack.
  - **History is rescaled with the numbers:** when the upgrade multiplies or divides an item's stock, its past stock changes are rescaled in storage too, so history reads in what it's bought in. It's part of the Storage port (`applyStockChanges` with `rescale`), with a contract test, so every adapter does it. *Alternative:* leave history as it was, in the old unit.
  - **Changing Bought in to what it contains** (bought in boxes, containing 20 tea bags, changed to tea bags) clears Contains, a usage in tea bags becomes one in what it's now bought in, and the numbers stay as they are: the app and `change_item` say what they now read as, to correct the count. *Alternative:* multiply the numbers, which is counting again.
  - **Assistants tidy both ways:** `change_item` clears To tidy whenever it sets `bought_in`, `contains` or `weight`, and `looks_right: true` clears it as it is.

  Kept from 0.10.0 as first built: Larder takes a little out every day for something used by weight, so stock reads "about ¾ jar" part way through; stock is kept to thousandths, so Larder waits a day or two when a day's amount doesn't round cleanly (5 g of a 400 g jar is 0.0125: it takes 0.025 every 2 days), keeping within 1% without storing a remainder; and a plain Use of something used by weight takes a whole one and doesn't start a period.
- **The Claude app through Home Assistant:** connectors that sign in (the Claude app, ChatGPT) work at `https://<home-assistant>/api/larder/mcp`. The integration offers the standard connector sign-in there; signing in is Home Assistant's own login, then an "Allow Claude to use Larder?" page; Larder issues the connector a Larder token as that Home Assistant user. Home Assistant tokens still work for clients that send one.
- **Add by photo** (the `ai` module): its own button beside Add by name, separate from Scan (since 0.5.2 it opens the scanner, with **Take photo** under the camera since 0.7.2; see "After the owner tried it"). Claude and Gemini, each with its own API key and model (Claude starts on Haiku, which reads labels well for a fraction of a penny), asked in the order set in Settings → AI: when the first can't (out of credit in a month without Max, say), the next reads the photo. Either can be switched off for a while without losing its key or model. A Claude subscription doesn't pay for it: Max includes monthly API credit for your own key, Pro doesn't. What the AI reads fills in Add item to check, never saved straight away; a shop Larder doesn't have is offered first ("Add Tesco?"). From an assistant app with Larder connected (Claude, or Gemini where it can connect), the assistant reads the photo itself and uses `add_item`, which now takes the brand and asks before adding a shop.

- **Online shopping** (the `online-shopping` module, 0.6.0), from the owner's design for shopping providers (`SPEC.md` in `larder-provider-tesco`): Larder holds the stock and buying rules and makes every decision; each shop's website is driven by a separate provider service behind one versioned contract (1.x), Tesco first. Providers stop at the basket. The owner chose:
  - **Shop favourites wait in Pending, beside shared links**, rather than a list of their own (the Sharing module's Pending page offers a slot for them).
  - **Perishables are capped by usage history**: never more than gets used within the shelf life (daily use from the last 90 days of stock taken out); with no history, something that keeps under 90 days only tops up to the normal amount, never the on-offer one.
  - **"Stock up to" is an ordinary item setting in the core**, so every shop's list suggests topping up to it, not just the online shop. The on-offer amount and target prices belong to the module.
  - **Built in one go** (five steps, one commit each) as one pull request.
  - **A link doesn't decide where something is bought:** the online basket only takes what belongs on that shop's list (its shops, or "any shop" and the shop sells its category). Linking a product to an item with no shop makes that shop its shop; an item already set to another shop keeps it, and the summary says it's linked but bought elsewhere.
  - **Things put on the list by hand are bought online too**, up to the stock-up amount (at least one pack), and come off the list once they're in the basket.
  - **A filled basket is a pending order** (the owner's idea): a new core stock state, ordered but not confirmed. It counts towards stock, so nothing is ordered twice online or in a shop, but it isn't on the way. Home and the item's page have **Confirm** and **Remove**; the order email's automation confirms it by calling `add_expected` as before (the same shop's pending order is confirmed rather than added). A delivery marked arrived takes the whole pending order if none of it was confirmed, else only what was, and says how many are still pending.
  - **Larder Automations is how Larder reaches its shops** (following the owner's hub in `larder-automations`): one address and token for the Mac, its automations listed there and each linked to one Larder shop, and waking and sleeping the Mac set once on the hub and shared by every automation. A provider at an address of its own still works, for a shop not run by the hub.
  - **Starting a shop in the app picks a day first**: tomorrow and the six days after as buttons (another day in words too), each day's free slots, book, then fill. Larder remembers the slots listed in the last hour, so a slot from a day looked at earlier can still be booked.
  - Kept as built: target prices per one of the item's own unit (per kg or litre for things counted in g or ml); the multibuy allowance as a percentage (25%); summaries and "log in again" as Larder events for Home Assistant automations to notify; waking through Home Assistant (`callService`); and booking only a slot from the last list (adding the slot's times to the contract's booking answer, a 1.4, would lift that).
- **Offline copies** (0.8.0, the owner's request: "an offline copy of the app where I download revisions of the database, and the app says load data from and lists them, so I can search"): for when the Wi-Fi is down and all that's left is a phone. The phone keeps the app itself (a service worker) and copies of what Larder shows, saved on the phone. With no connection Larder still opens, says it can't reach the server, and lists the copies under **Load data from**, newest first. A loaded copy works like the app: search (nicknames, places, codes, barcodes), items, places, stock filters, shopping lists, scenarios and recipes, with a bar saying which copy it is and a way back to the live Larder. A copy is the API's own answers to every page the app reads, saved by the server in one go (`GET /api/v1/offline/copy`) as the person asking, so it shows exactly what they could see. Modules add their pages with `ctx.addOfflinePaths` and `offline: true` on the web module.

## Architecture (agreed before Phase 1)

- **Runs on its own first:** Larder is fully supported outside Home Assistant from Phase 1. It ships as one Docker image with a Docker Compose example, its own household login and access tokens (for MCP and the integration), settings through environment variables, and a setup guide. HTTPS is provided by the person running it (reverse proxy, Tailscale or Cloudflare Tunnel).
- **Home Assistant follows:** the add-on is a thin wrapper around the same image, and the custom integration talks to Larder only through the REST API, so it works whether Larder runs as an add-on or elsewhere.
- **One data folder:** SQLite database, photos and scheduled backups all live in one folder, so a backup is a copy of that folder.
- **Swappable back end (ports and adapters):** core services never touch the database directly. Storage, files, search, events and login are each behind a small documented interface, with SQLite, local disk and in-app search as the defaults and an in-memory storage adapter for tests. Every storage adapter must pass one shared contract test suite. The core avoids SQL-only features: IDs are app-generated strings, queries are named store methods rather than joins, and multi-step changes are single storage operations. The UI, integration and MCP use only the REST API, so a whole replacement back end that implements the OpenAPI spec (and passes the API test suite) would also work.
- **Testing Home Assistant parts:** the integration gets unit tests with `pytest-homeassistant-custom-component`, end-to-end tests against a real Home Assistant running in Docker, and `hassfest` and HACS validation in CI.
- **Language:** TypeScript throughout (server, web app, MCP server). Python only for the Home Assistant integration.

## Phase 1: how it was built

These follow from the decisions above; the owner can change any of them.

- **Runtime:** Node.js 22.13 or newer (Docker image uses Node 24). SQLite comes from Node's built-in `node:sqlite`, so there are no native add-ons and the same image runs on ARM (Raspberry Pi) and x86.
- **Storage format:** each SQLite table holds whole JSON documents plus a few indexed columns, mirroring a document database so a Firestore adapter is a straight swap.
- **Server:** Fastify with zod schemas; the OpenAPI spec is generated from them and committed as `docs/openapi.json` (a test fails if it's stale).
- **Login:** `LARDER_AUTH=local` (default) gives household accounts with cookie sessions and hashed bearer tokens for integrations; `none` is for trusted networks. Home Assistant ingress login is Phase 2.
- **Web app:** React with hash routing and relative paths so it works behind Home Assistant ingress and reverse proxies. Fonts are bundled, so nothing loads from the internet.
- **Reverse proxies:** Larder ignores `X-Forwarded-*` headers unless `LARDER_TRUST_PROXY` names the proxy, so nobody can fake their address to dodge the sign-in limit (10 tries per address, 30 per account, in a few minutes).
- **Photos:** only JPEG, PNG, WebP, GIF, HEIC and AVIF, checked from the file itself, and served so they can't run scripts.
- **Lookup photos are saved, not linked** (added after Phase 4): when a scanned barcode is named, the photo the lookup found is downloaded once into Larder's files, so it's in backups and works offline. It becomes the item's photo if it has none, and that brand's photo either way. Only the address a lookup provider gave is downloaded (never one sent by a caller), only over https, up to 5 MB, and only if the bytes are a photo; if any of that fails the item is still saved, without a photo.
- **Photos for items added by name** (the owner's choice, added in 0.5.0): when Claude adds an item with a barcode, it gets the same photo a scan would. With a brand instead ("Flahavan's porridge"), Larder searches Open Food Facts (`search.openfoodfacts.org`; the other Open Facts sites have no search) and uses the photo of the product that really is that brand, has every word of the name, and has the fewest other words, so "Quaker porridge oats" gets Quaker Porridge Oats rather than a blueberry one. The same brand is often listed many times (Heinz baked beans over 150), so "only when one or two match" would almost never find one; the photo may be another pack size of the same product. With no brand nothing is searched, since a generic "porridge" would get some random brand's box. Only the name and brand are sent.
- **Shopping ticks** are kept on the phone until "Done", then sent in one go.
- **Barcode lookups** ask Open Food Facts, Open Beauty Facts and Open Products Facts in turn (4 seconds each). Answers and misses are cached; misses are retried after 7 days.
- **Licence:** MIT (the owner's choice, made when the repo went public).
- **Sharing from a phone** (the `sharing` module): Android's share menu → Home Assistant, which the integration forwards to Larder. A shared link waits in **Pending**, a list next to the Wish list (the owner's choice), and from there goes on the wish list or into Larder (the Add item page, filled in). The item keeps the link and where it came from (shop, app, phone, when, the price then). Not a separate Larder entry in the share menu, which would need Larder at its own https address outside Home Assistant.
- **Scanning is scan, Add, next** (the owner's way of working): a new barcode is named, remembered and added in one press; how many is on the card, but where it goes is a line with "Change", not a picker, and its type isn't asked. Tidying up (places, types) happens later, under Stock → **To tidy**. On a phone the result docks at the bottom of the screen.
- **Add by photo is part of the scanner** (0.5.2, the owner's ask after using both): **Read with AI** under the camera reads the pack, and a barcode nothing knows has **Read it with AI** on its card. Either way it's the same quick card as a new barcode (check the name, Add 1, next), not the Add item page, so photos fit the scan, Add, next flow; tidying is later. The core scanner doesn't know about the AI module: the module offers a `photoReader` through the web SDK. The Add by photo button stays, and opens the scanner ready.
- **The scanner's photo button is a shutter** (0.7.2, after the owner couldn't find how to take the picture): a small **Read with AI** button wasn't recognisable as one, and after pressing it the live camera kept moving with "Paused: finish this one first", which read as waiting for something else. Now it's a big **Take photo** button like Add from receipt's, the photo stays still in the viewfinder while the AI reads it, the chip and card say "Reading the photo with Claude…", and a double tap sends one photo.

The AI matches lines to the household's items and is told no match is fine; unmatched lines are shown and left out, with **Match** to pick one by hand. What a shop called an item is remembered once added, so vague receipt names ("HNZ BKD BNZ") only need matching once. Ticked by default: lines matched before, and the AI's sure matches; guesses are shown unticked. Added through the shopping list's purchase, so prices paid feed the pricing module like a shopping trip.
- **No HACS check in CI** (the owner doesn't use HACS: the add-on installs the integration). The integration can still be added to HACS by hand as a custom repository.
- **Home on a big screen doesn't repeat the sidebar** (0.6.1, the owner's ask): Scan, Add by name and the modules' ways to add (Add by photo, Add from receipt) are at the top of the sidebar, so Home leaves them out and starts with Going shopping. Put away goes too: it's one of Scan's modes. On a phone Home keeps them, since the tab bar only has Scan.
- **Places are set up from inside them** (0.6.1, the owner's ask: "I am in the room, let's add a space, edit the space"). Adding a place opens it, ready for its first spot. Spots are added in a row at the end of the list (type, Enter, type the next) and renamed with their pencil, without leaving the page. A room shows its spots first; a shelf or box shows what's on it first.

Something new is scanned from the spot (**Scan here**: the quick scan card with the spot filled in), or added by name with the spot filled in. Out-of-place stock and rechargeables are changed on the item's page.
- **To sort** (0.6.1, the owner's ask): stock added without a place waits in a pile at the top of Places until someone puts it away, rather than only under Stock → To tidy (which also lists things with no type). Putting it away moves only that stock, not the item's stock elsewhere.
- **Larder reads order emails after all** (0.7.0, the owner's ask; the brief had left email to a separate Claude automation). Gmail only, read-only (`gmail.readonly`), through the household's own Google Cloud client, which the app walks through step by step; Google sends the person back to Home Assistant's outside address (Nabu Casa, the owner's suggestion), where the Larder integration passes the sign-in on. ## Phase 2: how it was built

- **One image:** the add-on runs the same Docker image as the standalone install (`ghcr.io/doonetheprune/home-inventory`, tagged with the version in `addon/config.yaml`). The image starts as root only to give the data folder to the `node` user, then drops to it, so Docker volumes, bind mounts and the add-on's `/data` all work.
- **Ingress login:** people opening the add-on from Home Assistant are signed in as their Home Assistant user, from the headers Home Assistant's Supervisor adds, and only on connections from the Supervisor's address (172.30.32.2). Accounts are keyed by the Home Assistant user id (required). They are admins in Larder unless the add-on's **Larder admins** option lists who is.
- **Cold backups** (0.7.3, the owner's choice): Home Assistant stops the add-on while it copies `/data`, then starts it again. The SQLite database runs in WAL mode, and a backup taken while Larder is running could copy the database and its write-ahead log at different moments if something writes meanwhile (a timed order-email check, say), so it might not restore. A few seconds without Larder (its sensors unavailable), usually overnight, was preferred to the alternative: a snapshot made just before each backup and restored from afterwards, which needs more code.
- **Zero-setup integration:** the add-on keeps an access token for the integration in its data folder and announces itself to Home Assistant (Supervisor discovery), so the integration only needs confirming.
- **Sensors and actions come from Larder:** the integration builds them from `GET /api/v1/automation` at runtime, so new ones (core or modules) need no Python change. `services.yaml` is generated from the same list for Home Assistant's validator.
- **Names, not ids, and never a guess:** actions take items, places and shops by name, alias, code or barcode. Only an exact name, or a name containing every word given ("drill" → Cordless drill), is acted on; typos and look-alikes ("AA" when there are only AAA batteries, "salt" and Malt vinegar) are offered back as "did you mean", never acted on.
- **Events:** every Larder event is fired in Home Assistant as `larder_<type>`. Expiry is checked hourly, and each batch is announced once when it becomes due and once when it expires.
- **NFC:** the integration forwards every `tag_scanned` event; Larder resolves it and fires `larder_nfc_scanned`. Unknown tags are linked from the product or place page within 15 minutes of scanning. Android Chrome can read tags directly too.
- **Batteries:** a module. The integration sends every device with a battery sensor (and Battery Notes type and count, if installed); low is below 20% (option) or a battery-low binary sensor turning on. Larder answers swap / charge / spare / on the way / buy, and puts batteries on the shopping list when there are none.
- **Own backups off in the add-on:** Home Assistant backups already include `/data`; Larder's daily copies can be turned on in the options.
- **The add-on installs the integration** (the owner's choice, added after Phase 4, so a private repo needs no HACS): the image carries the matching `custom_components/larder`, and on start the add-on copies it into Home Assistant's config when it's missing or older, then shows a "restart Home Assistant" notification. It never downgrades one that's newer (from HACS, say), and an option turns it off. This needs write access to Home Assistant's config folder and the Home Assistant API, so Home Assistant shows the add-on with a lower security rating. The copy runs as root before Larder starts; Larder itself still runs as the unprivileged `node` user.
- **Version 0.2.0:** app, add-on and integration versions move together (a test checks).

## Phase 3: how it was built

- **Tools live in the core** (`core.assistant`), the MCP server only serves them, so the same tools could be offered another way later. Modules add theirs with `ctx.addTool`.
- **Few, plain tools** (13 with pricing): search, get_item, add_item, add_stock, use_stock, move_item, add_expected, mark_arrived, add_to_shopping_list, shopping_list, expiring, check_price, set_usual_price. They answer in short readable text, because small local models handle that better than JSON. Write tools reuse the Home Assistant actions' wording.
- **Stateless Streamable HTTP with JSON answers** at `/mcp` (official MCP SDK 1.32): no sessions or open streams, so it passes through Home Assistant, proxies and tunnels.
- **Three ways in:** a Larder token on `/mcp`; a Home Assistant token on `/api/larder/mcp` (for Nabu Casa); connector sign-in (OAuth with PKCE and dynamic registration) when Larder has a public https address.
- **Connector tokens are ordinary Larder tokens** named after the assistant and where it signed in from ("Claude (via claude.ai)"), revocable in Settings. They don't expire.
- **Guard rails on open registration** (after review): anyone can register a client, so Larder caps registrations per address (30 an hour) and in all (200, making room only by forgetting clients that never signed in), caps sign-ins waiting for approval, shows its own error page instead of redirecting, and the approval page says to check the address.
- **No changes from other websites**, in every sign-in mode: a write that a browser marks as coming from another site (Sec-Fetch-Site, or a foreign Origin) is refused unless it carries an access token or the web app's header. Only `/oauth/token` reads form posts.
- **MCP hints:** tools that take away or overwrite (use_stock, move_item, mark_arrived, set_usual_price) are marked destructive, so clients can ask first. (Narrowed in 0.9.1: see "Assistants ask less" under "After the owner tried it".)
- **Version 0.3.0.**
- **The connector can do what the app does** (the owner's request, after trying the Claude app; replaces "few, plain tools"): shops, places and storage grids, categories, changing or removing an item, brands and barcodes, correcting a batch, deliveries and recent changes, and everything on the scenarios and recipes pages. 54 tools with every module on. Left out on purpose: accounts, access tokens, household settings, backups and module switches (so a connector can't widen its own access), and photos, NFC tags, printing and shop locations (they need a camera, a tag, paper or the map pages). *Alternative:* a smaller set for small local models, which would then need the app for these.
- **Recipes on items and in scenarios** (the owner's request): an item's page lists every saved recipe that uses it, and a recipe's linked ingredients open their item. A recipe can belong to scenarios and be kept for them only, so seasonal recipes (Halloween, Christmas) stay off the main list; they're folded away under "Kept for scenarios" there, and listed on their scenario's page, where "Add one" starts a recipe kept for that scenario. If its scenarios are removed or switched off, it comes back to the main list. Modules show panels on each other's pages through slots in the web SDK, without importing each other.
- **A shop, place or category that isn't set up is never left out quietly:** `add_item` refuses (adding nothing) and says to offer adding it first, naming `add_shop` (common UK shops come with what they sell), `add_place` or `add_category`.

## Phase 4: how it was built

- **All four extras are modules**, using only the public core, the web SDK and new general hooks: module pages with parameters and a Print section, `QrCode` and `PrintSetup` in the SDK, a `demo` hook for example data, and `core.stock.useMany` (several uses at once, all or nothing).
- **Scenarios** are tags on products (`product.fields.scenarios`), so deleting an item takes it out of every scenario. No target quantities. A scenario is grouped by where things are now, with out-of-place stock marked.
- **Printing:** label positions use the Avery templates' measurements (L7160, L7163, L7651) plus plain A4 with cut lines; print at 100% with no margins. Only the page's `print-area` prints. Scenario pages print on A4 with 12 mm margins, with place photos if the places have them.
- **Recipes:** ingredients link to items only when the name clearly is one (the same strict matching as actions); quantities to take are in the item's own unit. Cooking is always propose, then confirm (with changes), never automatic.
- **MQTT:** off by default; retained stock and sensor topics, plus every event; no Home Assistant MQTT discovery (the integration is the Home Assistant link). The add-on uses the Mosquitto add-on automatically.
- **Third-party packages in modules** are allowed only when listed for that module in the architecture test (MQTT uses `mqtt`).
- **One change at a time** (after review): stock writes and product updates go through one queue in the core (`ctx.exclusive`), because two changes at the same moment (two automations, a double tap) could both start from the same stock and one would be lost. Modules change their own product field with `core.products.updateField`, and find their own things by name with `core.resolve.among` (the same strict rules as items). The queue is per process, which suits Larder (one process); a storage adapter for several instances would need database transactions instead (noted in ARCHITECTURE.md).
- **Version 0.4.0.**

1. **The add-on needs the image to be downloadable.** While the repository is private, Home Assistant can't pull the image without registry credentials (Settings → Add-ons → Registries). *Alternative:* make the repo and package public, which also unlocks HACS.
